# Security incident response and credential rotation

This runbook applies to MoonWitness source, GitHub automation, API authentication, database access, and stored application data. Use it with [the public reporting policy](../../SECURITY.md). It describes response actions; it does not assert that production infrastructure, a GitHub App, cloud storage provider, or private reporting channel is currently configured.

## Roles and record

- The repository owner is incident commander until another person is explicitly assigned. The commander records incident ID, severity, affected SHA/releases, start/detection time, decisions, and recovery evidence in a private, access-controlled record.
- Assign a technical responder for containment and verification. Assign a privacy/legal contact when user data or regulated obligations may be involved; confirm notification duties and deadlines with qualified counsel rather than inferring them here.
- Keep sensitive evidence private. Record hashes, timestamps, affected secret names, and sanitized request IDs; never copy secret values, session cookies, exploit payloads containing real data, or raw credential-bearing traces into GitHub issues, CI summaries, or this repository.

## Severity and first response

Treat active unauthorized access, authentication/authorization bypass, exposed signing/database credentials, confirmed user-data disclosure, or malicious release artifacts as **SEV-1**. Treat a contained vulnerability with no evidence of exploitation as **SEV-2**. The incident commander may raise severity at any time.

1. Acknowledge privately; preserve the report and establish a private incident record. Do not ask the reporter to publish proof.
2. Identify affected assets, credential names, commit/release range, access window, data scope, and whether exploitation is ongoing. Assume an exposed credential is compromised; absence of observed abuse is not proof it was unused.
3. Contain first: revoke or disable the affected credential at its issuer, suspend the affected integration/workflow if necessary, restrict access, and stop unsafe publication. Do not rewrite a published Git tag or erase incident evidence.
4. Rotate dependent credentials from a trusted machine and secret manager. Update every consumer, restart/redeploy only the affected service through its approved operational process, and revoke the old credential after the replacement is verified. Do not paste secrets into shell arguments, chat, PRs, or logs.
5. Review GitHub audit events, workflow runs, PR/ref changes, release assets, database/auth audit records, and storage access for the exposure window. Preserve relevant evidence and note unavailable telemetry as unknown.
6. Restore service from a known-good source, verify health and access boundaries, communicate privately with affected parties, and document corrective actions. Consult the privacy/legal contact for any notification obligations.

For repository secrets, use GitHub's protected Actions secret settings or an approved secret manager. Do not use plaintext workflow inputs or print values to confirm a change. If a secret entered Git history, revoke it first; removal from current files does not invalidate old commits or cached artifacts. Follow the repository's protected history-rewrite/incident decision separately—never force-push around branch protection.

For an incident requiring global refresh-session revocation, `pnpm revoke:auth-sessions` is plan-only and requires an explicit `DATABASE_URL`; it reports the target host, port, database name, and outstanding-session count, never the connection string. After reviewing that plan, apply with `pnpm revoke:auth-sessions -- --apply --all --confirm-host=<exact-host> --confirm-port=<exact-port> --confirm-database=<exact-database-name>`. This revokes refresh sessions for every account and forces users to sign in again. It does not delete users or access/audit records. Do not run it for a single-user password event; use that user's password-change/reset flow instead. The command refuses a mismatched target and does not install or upgrade schemas.

## Correct a vulnerable or compromised release

1. Identify the exact source SHA, tag, image digest, checksums, SBOM/provenance, affected versions, and exploitability. Preserve the original immutable identity for investigation.
2. Contain publication or advise consumers to stop using the affected artifact. Mark the release as affected/superseded and publish a coordinated advisory without exposing a working exploit prematurely.
3. Implement the fix on `dev`; promote through the existing `dev` → `main` PR, required CI, and security/CODEOWNER approval. Build a **new** patch version and new immutable tag/artifacts from the reviewed main SHA.
4. Verify the new artifact digest, SBOM/provenance, checksums, and clean security scans. Publish the correction notice and upgrade/mitigation guidance. Do not move or overwrite an existing tag, release asset, image digest, or attestation.
5. If release automation is unavailable, use the documented repository release process with equivalent approvals and record the deviation; do not deploy application services from a release workflow. Application deployment remains an operator-controlled activity outside this repository's automated release flow.

## Tabletop: `JWT_SECRET` appears in a pushed commit

Use this scenario to rehearse without creating or exposing a real secret:

1. Detection: record the commit SHA, first detection time, affected environments by secret **name**, and CI/artifact locations that may have copied the value. Do not quote the value.
2. Containment: incident commander assigns a responder; suspend any workflow that could publish the value; restrict access to affected logs/artifacts; rotate `JWT_SECRET` in the secret store and restart all API instances. Then review the plan from `pnpm revoke:auth-sessions` and apply with explicit all-session/host/port/database confirmation. Treat all old sessions as compromised.
3. Validate: old JWT and old refresh tokens are rejected; fresh login and refresh work; `/livez` and `/readyz` pass; audit records show no unreviewed privileged changes. Check GitHub audit/workflow activity and database/auth logs for the exposure window.
4. Recover and communicate: restore approved workflows, notify affected users privately if evidence/scope requires it, consult privacy/legal owner, and publish a new corrected release only when a shipped artifact was affected. Preserve the bad commit and its incident linkage; history cleanup requires a separate owner decision after containment.
5. Closeout: record source/release identity, systems checked, telemetry gaps, rotation verification, user impact, corrective actions with owners/due dates, and a retrospective. Do not close while access scope or required notification decisions remain unknown.
