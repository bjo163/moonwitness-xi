# Evidence K4-004 — scoped theology and semantic concept profiles

## Status

- Status: in progress; this batch defines scoped profiles and implements a transaction-bound canonical evidence resolver. It does not add source-backed RUH/HIZAB mappings or an HTTP profile persistence/API surface.
- Date: 2026-10-17 (Asia/Jakarta).
- Dependencies: K4-002 semantic annotation and K2-004 revelation identity/edition ontology.
- Scope: `ontology/domains/concept-profile.schema.json`, schema-backed validation in `@moonwitness/research`, and synthetic concept/review fixtures. The approved existing Q7:46 sample is used only to verify local provenance; it receives no lexical gloss or theological mapping here.

## Implemented

- Added a versioned JSON Schema for concept profiles with a stable concept ID, distinct profile ID, tradition, optional community/school and language, interpretive scope, epistemic status, explicit uncertainty, and one or more human interpretations.
- Multiple profiles may describe the same concept while retaining separate tradition/community scopes and different interpretations.
- Each interpretation is explicitly `human_interpretation`, never revelation. Accepted interpretations must name at least one evidence ID; candidate and rejected interpretations remain representable.
- Synthetic tests prove divergent profiles remain separate and reject revelation claim types, missing uncertainty, and accepted interpretations without evidence IDs.
- Added `validateConceptProfile` as the package structural validator and `validateConceptProfileWithEvidence` for accepted interpretations. It requires a trusted resolver to return matching valid canonical evidence metadata, accepted nonconflicting review consensus, and readable access; missing, mismatched, denied, malformed, or throwing resolver results fail closed.
- The async validator snapshots the entire input before awaiting a resolver and rejects any caller mutation detected before completion. Tests cover evidence-ID injection, candidate-to-accepted mutation, and malformed resolver results.
- Added optional `textual_observations` separate from `human_interpretation`. An observation stores only the canonical source/edition/locator/hash, Unicode-scalar range, digest of the selected span, and `unreviewed` state; it does not copy selected text or assert a gloss, translation, doctrine, or concept mapping.
- Added `validateConceptProfileTextualObservations`, which fails closed on missing/malformed/denied or mismatched canonical passages, source hash mismatch, invalid ranges, selected-span digest mismatch, and input mutation during resolver awaits. The trusted resolver must itself read and verify local source bytes and rights metadata; the package contract is not an authorization boundary.
- Added `resolveConceptProfileEvidence` in `@moonwitness/orm-knowledge`. Within one PostgreSQL transaction it rechecks active user/role/company membership, locks and loads the active immutable graph snapshot, binds the evidence record to its exact Assertion and `content_revision`, enforces the INTERNAL visibility ceiling, and verifies the locally pinned passage bytes/hash.
- The resolver derives active-company review consensus from digest-checked, schema-checked review events joined to their workflow instance/event, exact resource record, reviewer/requester canonical identities, reviewer role, action, revision, and idempotency key. Acceptance requires an independent accepted decision for the current release digest and evidence ID; a conflicting outcome for the exact Assertion revision fails closed. Stale-release acceptance is not carried forward.
- Added synthetic ORM/workflow tests for accepted and unreviewed states, conflicting outcomes, inactive company membership, and Assertion revision changes. The fixture reuses only the already approved local Tanzil Q7:46 snapshot to verify provenance; the assertion and all review/workflow identities are synthetic, with no cross-source or theological claim.
- No source text or substantive RUH/HIZAB interpretation was added. Resolver fixtures use synthetic graph assertions, actors, and review/workflow events; only the approved local Q7:46 passage is read to prove source provenance.

## Remaining acceptance

- Integrate the ORM resolver into any future server-side concept-profile read/write flow using authentication middleware context; do not accept identity or review status from request/profile fields. No HTTP or concept-profile persistence surface is included in this batch.
- Add source-backed RUH/HIZAB profiles and mappings only when their sources and usage are explicitly authorized; preserve divergent readings and scope.
- Keep all profiles interpretive and noncanonical unless separately reviewed under the repository's governance.
