# Evidence M11.08 — Trusted maintainer issue intake

## Status

Partial. A deterministic, side-effect-free intake planner now converts normalized issue events into bounded maintainer proposals. It cannot accept roadmap state, modify source, write GitHub, execute a command, choose a ref, or fetch an issue-provided URL. M11.08 remains unchecked because GitHub event authentication/permission adapter, durable delivery deduplication, and hosted workflow acceptance are not implemented.

- Source branch: `dev`.
- Scope: `scripts/roadmap/issue-intake.mjs`, `scripts/roadmap/issue-intake.test.mjs`, `package.json`.
- Remote issue mutations: none performed.
- Runtime issue event workflow: not enabled; no webhook event is currently wired to this planner.

## Contract

- Caller supplies the numeric repository identity, stable delivery ID, issue number, managed Task ID, action, and actor identity. Before calling this pure planner, a future adapter must authenticate the GitHub webhook/delivery and fetch or validate the actor's current maintainer permission through an authoritative source. An `actor` field in untrusted event JSON alone is not authorization.
- Only repository-matching, explicitly allowlisted maintainer actors can create a proposal. Known bot actors and pull requests are ignored to prevent sync echoes.
- Accepted proposal types are roadmap status, scope, issue close review, and issue triage. Status and scope remain proposals for a maintainer source change on `dev`; neither changes the roadmap nor its evidence.
- Close/reopen events without accepted evidence become triage proposals. Even with accepted evidence, close becomes a review candidate and requires the lifecycle reconciler to prove delivery gates.
- Unknown actions/statuses, malformed Task IDs/issue IDs/delivery IDs, empty text, and oversized proposal content fail closed. User-supplied text remains inert; this module has no shell, Git, HTTP client, or GitHub API dependency.
- Proposal delivery ID is carried to support consumer-side deduplication. It is not persisted here, so it does not itself provide exactly-once processing.

## Verification

- `pnpm test:roadmap`: includes fixtures for trusted/untrusted actors, bot echo, PRs, repository mismatch, unsupported command/status, inert arbitrary text, close/reopen triage, accepted-evidence close review, invalid identities, and bounded text.
- `pnpm lint`, `pnpm format:check`, `pnpm automation:check:roadmap`, and `git diff --check`: run for this unit before commit.
- Hosted CI for implementation SHA `cc2d39e2537b45393b6cfca0737178f3776cfa0e` (run `37519002276`): plan, UI, automation, containers, quality, browser, and integration jobs passed. `ci-gate` stopped only at “Require fresh CODEOWNER approval for sensitive promotions”; no bypass was used. CodeQL, Gitleaks, Pages, and roadmap issue plan runs also passed for the same SHA.
- No GitHub issue, comment, label, branch, commit, release, or deployment was written by intake.

## Remaining acceptance

- Build a workflow/adapter that verifies GitHub webhook signature/delivery and authenticates the current repository, issue marker, author/comment actor, and maintainer role without trusting body fields.
- Persist delivery IDs with bounded retention and test duplicate/out-of-order events and bot echoes against that store.
- Render proposal reports without secret/body leakage; require a maintainer-reviewed source diff and normal CI before any roadmap change is accepted.
- Exercise close/reopen triage and permission revocation in a hosted read-only pilot. Do not enable source writes or release actions from issue events.
- Only after these controls and the M8.04 security prerequisites pass, record hosted evidence and consider completing M11.08.
