# Evidence M11.08 — Trusted maintainer issue intake

## Status

Partial. A deterministic, side-effect-free intake planner plus raw GitHub issue-comment payload normalizer convert only explicit bounded commands on one managed issue into maintainer proposals. The normalizer derives a stable key from GitHub's comment ID, but no consumer persists/deduplicates delivery IDs. It cannot accept roadmap state, modify source, write GitHub, execute a command, choose a ref, or fetch an issue-provided URL. M11.08 remains unchecked because current actor permission verification, event workflow wiring, durable consumer deduplication, and hosted acceptance are not implemented.

- Source branch: `dev`.
- Scope: `scripts/roadmap/issue-intake.mjs`, `scripts/roadmap/github-issue-intake.mjs`, `scripts/roadmap/issue-intake.test.mjs`.
- Remote issue mutations: none performed.
- Runtime issue event workflow: not enabled; no webhook event is currently wired to this planner or normalizer.

## Contract

- Normalizer accepts an `unknown` GitHub issue-comment payload and expected numeric repository ID; it requires `action=created`, one exact repository/task marker, safe numeric issue/comment IDs, a human actor, and one bounded `/mw` command. It returns a deterministic `issue_comment_<comment-id>` key; it has no network or write capability.
- Before calling the pure planner in a workflow, the runner must rely on GitHub's authenticated Actions event context and fetch or validate the actor's current maintainer permission through an authoritative source. An `actor` field in a manually supplied payload alone is not authorization.
- Only repository-matching, explicitly allowlisted maintainer actors can create a proposal. Known bot actors and pull requests are ignored to prevent sync echoes.
- Accepted proposal types are roadmap status, scope, issue close review, and issue triage. Status and scope remain proposals for a maintainer source change on `dev`; neither changes the roadmap nor its evidence.
- Close/reopen events without accepted evidence become triage proposals. Even with accepted evidence, close becomes a review candidate and requires the lifecycle reconciler to prove delivery gates.
- Unknown actions/statuses, malformed Task IDs/issue IDs/delivery IDs, empty text, and oversized proposal content fail closed. User-supplied text remains inert; this module has no shell, Git, HTTP client, or GitHub API dependency.
- Supported command syntax is `/mw status <planned|in_progress|blocked|complete> -- <rationale>`, `/mw scope -- <proposal>`, `/mw close -- <rationale>`, and `/mw reopen -- <rationale>`. Comment text is copied only into an inert proposal.
- Proposal delivery ID remains deterministic across webhook redelivery of the same comment, supporting consumer-side deduplication. It is not persisted here, so exactly-once processing is not claimed.

## Remaining acceptance

- Wire the normalizer behind a read-only GitHub Actions event workflow and verify the actor's current repository write/maintain permission before proposal planning; fail closed if permission cannot be read.
- Add bounded durable consumer deduplication and test duplicate/out-of-order deliveries and bot echoes against that store; same-comment normalization alone is not a persistent idempotency guarantee.
- Render proposal reports without secret/body leakage; require a maintainer-reviewed source diff and normal CI before any roadmap change is accepted.
- Exercise close/reopen triage and permission revocation in a hosted read-only pilot. Do not enable source writes or release actions from issue events.
- Only after these controls and the M8.04 security prerequisites pass, record hosted evidence and consider completing M11.08.
