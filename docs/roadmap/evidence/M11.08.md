# Evidence M11.08 — Trusted maintainer issue intake

## Status

Partial. A bounded raw GitHub issue-comment normalizer and read-only adapter now check the actor's current repository permission before generating an inert proposal. A workflow reports only proposal metadata to the Actions summary and holds no write permission. M11.08 remains unchecked because delivery IDs are not durably deduplicated and the new workflow has not been activated and observed on the hosted default branch.

- Source branch: `dev`.
- Scope: `scripts/roadmap/issue-intake.mjs`, `scripts/roadmap/github-issue-intake.mjs`, `scripts/roadmap/issue-intake.test.mjs`, `scripts/roadmap/run-issue-intake.mjs`, `.github/workflows/roadmap-issue-intake.yml`.
- Remote issue mutations: none performed.
- Workflow source is wired for `issue_comment.created`; it uses exact event SHA checkout with credentials persistence disabled, and grants only `contents: read` and `issues: read`.

## Contract

- Normalizer accepts an `unknown` GitHub issue-comment payload and expected numeric repository ID; it requires `action=created`, one exact repository/task marker, safe numeric issue/comment IDs, a human actor, and one bounded `/mw` command. It returns a deterministic `issue_comment_<comment-id>` key; it has no network or write capability.
- Adapter binds numeric repository ID and case-insensitive repository full name, then checks the event actor through GitHub's current collaborator-permission endpoint. Only current `write`/`admin` permission can create a proposal. Missing collaborators, low privilege, API failures and malformed responses fail closed.
- Workflow uses GitHub's authenticated Actions event payload and asks the runner adapter to check current repository permission. It does not accept arbitrary actor allowlists from event text. Known bot actors and pull requests are ignored before making the permission request.
- Accepted proposal types are roadmap status, scope, issue close review, and issue triage. Status and scope remain proposals for a maintainer source change on `dev`; neither changes the roadmap nor its evidence.
- Close/reopen events without accepted evidence become triage proposals. Even with accepted evidence, close becomes a review candidate and requires the lifecycle reconciler to prove delivery gates.
- Unknown actions/statuses, malformed Task IDs/issue IDs/delivery IDs, empty text, and oversized proposal content fail closed. User-supplied text remains inert; only the adapter performs one fixed GitHub API GET, while the runner has no shell execution based on event text or write API call.
- Supported command syntax is `/mw status <planned|in_progress|blocked|complete> -- <rationale>`, `/mw scope -- <proposal>`, `/mw close -- <rationale>`, and `/mw reopen -- <rationale>`. Comment text is copied only into an inert proposal.
- Proposal delivery ID remains deterministic across webhook redelivery of the same comment, supporting consumer-side deduplication. It is not persisted here, so exactly-once processing is not claimed.

## Remaining acceptance

- The workflow source is present on `dev`; a GitHub Actions workflow only becomes active from the repository's default branch, so hosted activation still needs promotion and an observed run.
- Add bounded durable consumer deduplication and test duplicate/out-of-order deliveries and bot echoes against that store; same-comment normalization and Actions concurrency do not provide persistent exactly-once processing.
- Proposal summary omits comment body and rationale, and includes delivery ID, kind, task, issue, actor and source SHA. Require a maintainer-reviewed source diff and normal CI before any roadmap change is accepted.
- Exercise close/reopen triage and permission revocation in a hosted read-only pilot. The workflow cannot source-write or issue-write.
- Only after these controls and the M8.04 security prerequisites pass, record hosted evidence and consider completing M11.08.
