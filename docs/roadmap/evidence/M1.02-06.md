# Evidence M1.02–M1.06

- Branch inventory before rules: only `main` (default) and `dev` existed.
- M1.02: active repository branch ruleset `24436078`, “Two branches only: main and dev”, targets `~ALL` and enforces the `creation` rule. This blocks creation of every new branch/ref while retaining the existing two. A `branch_name_pattern` rule was rejected by GitHub validation; the creation rule is the stronger supported control. There are no bypass actors.
- M1.03: the same ruleset blocks deletion and non-fast-forward updates for both existing branches. There are no bypass actors; emergency changes require an administrator to change/disable the ruleset and should be recorded.
- M1.04: active ruleset `24436095`, “Protect main: promote from dev through CI”, targets `refs/heads/main`, requires pull requests, resolved review threads, and allows only merge commits. Since the branch-creation ruleset leaves `dev` as the only non-target branch, promotion is constrained to `dev → main`.
- M1.05 implementation: `.github/workflows/promote.yml` creates/finds one `dev → main` PR on every `dev` push and enables auto-merge with merge commit. Repository `allow_auto_merge` is enabled; delete-branch-on-merge remains false. The PR automation's successful remote behavior is pending its first run after this workflow is pushed.
- M1.06: `ci-gate` is configured as a strict required status check on `main`. Its real check-run name was verified as `ci-gate` on commit `26501bb`; the run passed all jobs and the gate. CI has no path filters and the gate rejects failed/cancelled/skipped/missing jobs.
- GitHub API verified both rulesets active, only `main`/`dev` branches present, `main` remains default, `allow_auto_merge=true`, and `delete_branch_on_merge=false`.
- Deployment constraint: GitHub Actions workflow `deploy.yml` was disabled on the repository because the copy on `main` could deploy staging after the first promotion. The workflow file is retained but its source on `dev` also has `on: []`.
- Limitation: source-branch is not a native rule parameter on this repository plan. Restricting creation of all new branches makes `dev` the only branch that can target `main`; future need for temporary branches requires revisiting this governance decision first.
