# Evidence M8.03 — Security scanning and vulnerability policy

## Status

- Status: implementation prepared; Board image fix and severity-aware gate require hosted verification; CodeQL findings remain under triage.
- Source SHA: `768571a44eb729e18c2eb11ef009045f3202e6f7` for the hosted scan that identified the Board image criticals; patched image is in the current follow-up.
- Scope: CodeQL JavaScript/TypeScript and Actions, locked workspace dependency vulnerability scan, critical severity gate, SARIF upload, and exception expiry validation.

## Delivered

- `.github/workflows/codeql.yml` runs on PR/push to `dev` and `main`, weekly, and manually. Only the analysis job receives `security-events:write`.
- The `containers` CI lane scans the root pnpm lockfile and built production API/Board images for vulnerabilities, uploads full-severity SARIF, and uses a local gate to block CRITICAL findings while failing closed on scanner errors or malformed reports.
- `docs/security/vulnerability-policy.json` defines the severity policy and starts with no suppressions. Any future exception must have an ID, owner, reason, and ISO expiry date; expired or malformed exceptions fail CI.
- Unit tests cover detection of a seeded CRITICAL result, scanner errors, and expired/incomplete exceptions.
- The first hosted CI attempt exposed an upstream Trivy composite-action reference to a nonexistent `setup-trivy@v0.2.1` tag before any job steps ran. The action was updated to upstream `trivy-action@v0.36.0`, whose composite pins `setup-trivy` to immutable commit `3fb12ec12f41e471780db15c232d5dd185dcb514`; the hosted rerun passed its workspace scan.
- Dependabot security updates were enabled through the repository API; secret scanning and push protection were already enabled. Non-provider-pattern scanning remains disabled after a settings update attempt, so that feature is not claimed.
- Hosted CodeQL on `c3cac688` succeeded and uploaded results, but reported High-severity alerts across password hashing, client regex, docs link validation, E2E random IDs, and workflow cache trust boundaries. These findings require triage; workflow success does not mean zero findings.
- Hosted Trivy on `899b149` uploaded 21 API image findings, including High and Medium findings. The step failed because Trivy action SARIF mode clears its severity filter by default to include all findings, so `exit-code: 1` also blocked on High findings. The uploaded SARIF did not show CRITICAL results. The workflow now separates complete report generation from a local CRITICAL-only SARIF gate and still runs all three scans when a scanner errors.
- The first full-severity SARIF gate on `768571a` correctly blocked the Board image for CRITICAL `CVE-2026-31789` in Alpine `libcrypto3`/`libssl3` (`3.3.3-r0`, fixed `3.3.7-r0`). `Dockerfile` now uses official stable `nginx:1.30.5-alpine`; a hosted rescan must confirm the finding is gone.
