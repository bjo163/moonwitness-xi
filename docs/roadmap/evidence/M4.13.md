## Contract and result

- PostgreSQL pool minimum/maximum, connection acquisition deadline, and server-side statement timeout are configurable with bounded validated environment values. Defaults are pool 0–10 per process and 30-second acquire/statement timeouts.
- The API accepts a constrained caller request ID or creates a UUID, returns it in `X-Request-ID`, and keeps health endpoints out of caches. Liveness is independent of PostgreSQL; readiness performs a DB check.
- API shutdown stops accepting new work, lets Fastify drain in-flight requests, closes active connections after 30 seconds, and closes the pool through the existing lifecycle hook. Shutdown failures produce a nonzero exit status.
- The scheduler, jobs worker, and outbox worker respond to SIGINT/SIGTERM, mark optional readiness probes unavailable, stop polling, drain active work according to the existing job/outbox semantics, close probes, and close the DB pool.
- Optional worker `/livez` and `/readyz` probes are disabled by default (`port=0`), bind to loopback by default, and do not expose readiness details beyond the worker name and state.
- Operational sizing, timeout, probe, request-ID, and shutdown contracts are documented in `docs/engineering/runtime-operations.md`.

## Limits

- Worker probe servers are disabled unless an operator assigns separate ports. When enabled, they should remain on loopback or a private network.
- Pool limits apply per process; operators must budget aggregate API replicas, workers, startup/maintenance tasks, and PostgreSQL reserved connections.
- The shutdown timeout bounds API socket draining. Job and outbox interruption recovery continues to depend on existing leases and at-least-once/idempotent delivery contracts.
