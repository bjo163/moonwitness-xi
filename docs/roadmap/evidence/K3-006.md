## Implemented

- Added `explainResearchRelation`, which accepts a validated graph snapshot, a relation ID, exact K3-002 evidence references, and local source/passage lookups.
- Explanations retain relation predicate/version/revision/scope and epistemic/review status; supporting evidence and counterevidence remain separate and include exact source, expression where applicable, edition, locator, hash, citation, excerpt, and Unicode range.
- Alternative hypotheses retain their own status and evidence. The projection does not narrate causation or infer ordering from timestamps; it includes the explicit `linked_evidence_only` interpretation boundary.
- Graph validation runs before projection. Relations, endpoints, scope, alternatives, evidence, and the assertions referenced by evidence must pass the caller-supplied access policy; evidence visibility must match its validated graph node, and relation visibility must dominate referenced evidence and assertion visibility. Inaccessible roots/records fail closed. Exact selectors are resolved against local pinned passage data and bad hashes/quotes are not explained.
- Before the first asynchronous passage lookup, the helper JSON-snapshots and validates the graph and evidence references and copies the visibility map. All authorization checks and output construction use those detached values; passage lookup and access callbacks are captured once, and callbacks receive detached records. Deferred-lookup regression tests verify caller mutation of relation fields, evidence ID/direction/selector, alternative evidence, and visibility cannot change the explanation or authorize a different snapshot.
- Added a standalone golden Q7:46 test using only the user-approved local Tanzil verse and its CC BY 3.0 attribution. Separate synthetic graph records test disputed status, both evidence directions, alternatives, and stable ordering using only that same pinned Q7:46 passage. No cross-tradition relation is represented by these fixtures.
- Added `GET /api/research/relations/{relationId}/explanation`. It calls `readActiveResearchGraphRelease` once inside a short PostgreSQL transaction, then closes the transaction before resolving any corpus file or building the projection. The response carries that snapshot's exact release digest; graph records and evidence selectors are derived only from that same verified release. No caller-supplied graph or raw ORM table projection is exposed.
- The API requires the existing authenticated context and allows `user` and `superadmin` only when the selected company and active company membership are rechecked inside the same PostgreSQL transaction that reads the active release. Trusted `system` callers bypass company membership. Stored `PUBLIC` is raised to an effective `INTERNAL` floor; the route permits `INTERNAL` only and hides restricted records. Evidence resolves through the existing local Quran/textual-witness passage readers, without network fetch. Responses use `Cache-Control: private, no-store`.
- API route tests use an injected/mock active-release reader and synthetic immutable release data. They cover anonymous access, user access with active membership, missing company and inactive-membership denial, trusted system access, hidden restricted records, one exact release digest and its evidence, failed local evidence verification, no-store, and generated OpenAPI registration. The PostgreSQL API integration suite also creates an isolated-schema synthetic graph release, activates it, and verifies that an authenticated request returns the exact active digest and Q7:46 evidence while an unauthenticated request is rejected.
