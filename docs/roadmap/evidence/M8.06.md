## Flow and safety boundaries

1. The workflow runs only when manually dispatched for `dev`; it records the current checked-out `dev` SHA and regenerates the read-only dependency plan at that SHA.
2. The requested package and exact safe target must match one package candidate from that fresh plan. The checked-out worktree must be clean and match the full source SHA. Ambiguous, missing, same/unknown, prerelease, stale, Actions, and major candidates fail before application.
3. Tests run in a detached disposable worktree. The candidate job has `contents:read`, checkout credential persistence disabled, and no publication credential. Lifecycle scripts run only in that isolated job without an injected GitHub token.
4. The executor uses pinned pnpm, changes every workspace manifest declaration for exactly one dependency, regenerates `pnpm-lock.yaml`, then fails if any unrelated tracked or untracked path changed.
5. The candidate workflow is configured to require frozen install, lint, format, typecheck, unit, PostgreSQL integration, Chromium Board E2E, UI catalog/budget, architecture, docs/portal, Board lint, container smoke, and workspace/API/Board CRITICAL Trivy scans before a candidate commit/bundle is created.
6. A separate write-enabled job downloads the bundle, checks bundle SHA, expected source parent, exact current remote `dev` SHA, and that only package manifests plus lockfile changed. It publishes with the M7.08 non-force expected-ref helper under `repository-write-coordinator`.
7. Since `GITHUB_TOKEN` branch pushes do not reliably start downstream push workflows, a post-publication job explicitly dispatches promotion and full CI after the writer lock is released. Promotion still uses the existing risk classification, PR, required checks, and CODEOWNER approval policy.
8. A stale head or failed candidate produces no `dev` update. If a human commit lands during tests, publish rejects the candidate; it must be recomputed and fully retested from the new SHA. It never rebases an untested candidate over user work.
