# Evidence M7.11 — Prevent stable latest rollback

## Status

Partial. The release publisher now compares a stable candidate against all published stable GitHub Releases and moves each `latest` image alias only when the candidate is strictly newer. Prereleases, equal versions, and older versions leave the alias untouched. Local policy/workflow tests pass; hosted registry behavior and atomicity across both image packages are not yet verified.

- Source branch: `dev`.
- Source SHA: recorded by the evidence commit after implementation.
- Policy: `scripts/release-latest-policy.mjs`.
- Workflow: `.github/workflows/release.yml`.

## Behavior

- The publish job reads all published (non-draft, non-prerelease) GitHub Release tags using paginated API calls under its existing serialized repository-writer lock.
- The policy uses semantic version precedence, not lexical string order. It rejects malformed `v*` stable release tags rather than guessing an ordering.
- A first stable release may initialize `latest`; a newer stable release can advance it; prerelease/equal/older candidates do not write the alias.
- Versioned images still publish for older stable release tags; this workflow does not yet reconcile conflicting existing image tags, which remains M7.13 work.
- When `latest` is advanced, the workflow compares its pushed OCI digest to the version-tagged image digest for each image.
- The GitHub Release itself is marked prerelease and never latest for RC tags; stable releases are explicitly published as latest only when their version is newer. An existing correctly typed release for the same tag is reused.
