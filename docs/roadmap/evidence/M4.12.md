## Contract

- Chatter now sends actual bytes to an authenticated upload endpoint and downloads by attachment ID. Upload binds metadata to a readable parent record using request row/company scope; download resolves the same scope and returns not-found for inaccessible records.
- Uploads are octet streams up to 10 MiB, limited to 20 requests/minute/IP, with a declared MIME allowlist, a safe filename up to 255 characters, a server-generated UUID storage key, and a SHA-256 checksum. SVG is excluded; downloads are forced attachments with `nosniff` and private/no-store headers.
- The server writes mode-0600 temporary files and atomically renames them before inserting metadata/audit/outbox in one DB transaction. A metadata transaction failure removes the new file. Storage keys are excluded from serialized records, generic query fields, views, and audit snapshots. Generic REST/JSON-RPC cannot forge attachment metadata.
- Archive retains bytes so an authorized restore works; hard delete removes the DB record and then the local file. A filesystem failure after DB commit can leave an orphan requiring manual cleanup; M9.02 retains automatic orphan reconciliation and object-storage work.

## Limits

- The local filesystem directory must be persistent and shared by API instances using the same database. The implementation does not provide cross-region replication or malware scanning, and the MIME value is declared by the client rather than detected from file content. Forced-download headers prevent active formats from being rendered inline.
- The Base add-on's seeded attachment is placeholder metadata without a binary object, so download returns 404 for that sample. Newly uploaded attachments contain real bytes.
- Automatic expiry/orphan reconciliation and cloud object storage remain open under M9.02. No app production deployment was performed.
- CODEOWNER approval remains a separate promotion gate; this work does not promote the source commit to `main` or deploy the app.
