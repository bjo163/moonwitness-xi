# Evidence M7.08 — Coordinate repository writers and reject stale refs

## Status

- Status: implementation and hosted technical lanes pass on `dev`; a hosted manual main-to-dev sync invocation also passed. That invocation was a no-op because `dev` already contained `main`; no hosted race-injection test or mutating expected-ref publication was performed.
- Scope: serialize GitHub jobs that publish repository artifacts or mutate refs, and require the expected remote SHA before the main-to-dev sync bot pushes.
- No new branch or application deployment is created.

## Changes

- Repository-mutating/publishing jobs share the `repository-write-coordinator` concurrency group: promotion PR operations, main-to-dev synchronization, release publication, Pages deployment, and Pages failure issue reporting.
- The coordinator uses `cancel-in-progress: false`, so a running writer is not cancelled by a newer request. GitHub may coalesce pending runs; sync is also scheduled hourly and can be manually dispatched, while promotion/release/Pages jobs re-evaluate their source state before writing.
- The sync workflow fetches and records the `dev` head, merges current `main` into that exact head, checks both remote heads again, then calls `scripts/push-expected-ref.mjs` with the expected `dev` SHA.
- The helper validates the full target ref and object ID, reads the remote head, refuses a stale expected SHA, and performs an ordinary non-force push. Git's fast-forward check remains the final race guard if a user advances the ref between the read and push.
- The helper test uses two clones of a temporary bare repository. A simulated human update between planning and publication remains at the remote and makes the bot fail; an unchanged target accepts a fast-forward.
- The expected-ref race tests run in the CI automation test step. Generated platform references and README were refreshed to list the new root script.

## Limits and follow-up

- This proves stale `dev` updates are rejected and same-target fast-forward writes work. It does not claim an atomic compare-and-swap Git push: ordinary Git refs have no expected-old-SHA push primitive here, so an update racing after `ls-remote` is rejected by non-fast-forward protection when it diverges; any retry must recompute against the new head.
- A shared GitHub concurrency group coordinates these jobs only within this repository and is not a lock for external actors. Branch rulesets and ordinary non-force pushes remain required protections.
- The release tag workflow retains a separate per-tag verification group; its publishing job joins the shared coordinator. Verification jobs can remain parallel because they do not write.
- The expected-ref helper's mutating hosted path is still not exercised: current main is an ancestor of dev, so the manual workflow exited successfully without merging or pushing. A real main advancement will exercise publish; a hosted race-injection test remains separate from this no-op run.
- Two CI runs report `failure` only because their `ci-gate` requires a fresh CODEOWNER approval on PR #24. All underlying technical lanes passed; promotion remains subject to the existing approval policy.
