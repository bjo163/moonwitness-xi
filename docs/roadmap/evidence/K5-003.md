# Evidence K5-003 — witness testimony and correction domain

## Status

- Status: in progress; the local contract and synthetic examples are implemented, but the actor-access acceptance gate is not met.
- Date: 2026-10-16 (Asia/Jakarta).
- Dependencies: K5-001 local-only intake and K3-001 assertion contract.
- Data: fabricated fixtures only. No real testimony has been imported.

## Implemented

- Added `@moonwitness/orm-knowledge` as a programmatic addon with three separate records: immutable-source testimony, numbered sourced corrections, and linked interpretations.
- Preserved source text for time, precision, and uncertainty. Each correction carries its own source label, locator, digest, actor, and asserted-time precision.
- Interpretation rows reference an assertion and evidence independently; they do not update or replace the testimony.
- New records default to `RESTRICTED`; generic-user model access is seeded as denied; addon menus are development-only.
- Added idempotently installed SQLite and PostgreSQL triggers that reject direct SQL `UPDATE` and `DELETE` on testimony, correction, and interpretation tables. The setup runs transactionally after model synchronization, so it covers both fresh installs and existing addon tables.
- Kept the database unique constraint on `(testimony_id, sequence)` and added simultaneous insert tests proving that only one correction can claim a sequence, even when both writes bypass ORM hooks.
- Added a JSON Schema contract, a synthetic seed for each record type, ORM and raw-SQL immutability tests, sequence/provenance checks, and workspace addon-conformance registration.

## Remaining acceptance and limits

- No row-level owner/tenant/actor authorization exists in the ORM contract. Denying the generic user group at model level is not a substitute for route-level authorization. Direct lookup, search, guessed IDs, export, projections, and cross-tenant denial are not proven.
- Database triggers protect against ordinary SQL update/delete paths, but a database owner or privileged operator can alter/drop the triggers or mutate underlying files. This is an integrity guard, not a tamper-proof audit system.
- The correction-sequence helper is a pre-insert check; a future authorized write adapter must check the next sequence and insert within a serialized transaction. The unique constraint prevents duplicate sequence values but does not by itself prevent gaps or define retry behavior.
- Retention, revocation, downstream invalidation, and workflow-specific privacy/safeguarding approval remain K5-002 and owner gates. Keep production and real-data intake disabled until those controls are implemented and independently verified.
