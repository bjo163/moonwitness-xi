# Evidence M9.01 — Notification addon

## Status

- Implementation is ready on `dev`; database-backed integration/E2E and hosted workflow confirmation are pending because this workstation has no `POSTGRES_TEST_URL`.
- Decision: add `@moonwitness/orm-notification`; retain `base.activity` for reminders and reuse `@moonwitness/jobs` outbox for delivery.
- Delivery contract: in-app is the only delivered channel. The email template is seeded as a demonstration, but its adapter records `suppressed`; no network-capable email path exists.
- Seed contract: two templates, four example per-channel preferences for the built-in system/superadmin users, model access, menus, and views are installed programmatically. The inbox itself starts empty so no fake business event is shown.

## Delivered behavior

- Typed `notification.template`, `notification.preference`, and `notification.notification` models with required links, state, delivery status, and a unique hidden event/recipient/channel idempotency key.
- Outbox enqueue writes through the caller's transaction. The consumer validates untrusted payloads, active recipient, active company membership, template and preferences; duplicate dispatches are ignored safely.
- API inbox, read acknowledgement, and channel preference endpoints require authentication and scope every operation to both the authenticated user and active company. The generic ORM record rule adds the same recipient and tenant boundary.
- Board has a separate notification bell/inbox and settings controls, with loading, error, empty, unread count, retry, and mark-read feedback; `ActivityBell` remains unchanged.
- API startup and outbox worker install the addon. PostgreSQL concurrent-install coverage, restore-drill fixture accounting, generated model/API/package docs, architecture diagrams, and CI unit-suite registration include it.
