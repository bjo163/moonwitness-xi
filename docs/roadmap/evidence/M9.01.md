## Current-state audit

| Existing component     | What it does                                                                                                        | Gap for a notification inbox                                                                                                                            |
| ---------------------- | ------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `base.activity`        | Stores reminders with summary, assigned user, due date, state, and linked resource.                                 | It is a task/reminder record, not an event inbox; there are no user delivery preferences, notification templates, or per-recipient delivery/read state. |
| Board `ActivityBell`   | Polls `base.activity` in planned state and lets users mark activities done.                                         | It surfaces work activities and must keep that behavior distinct from delivered messages.                                                               |
| `packages/jobs` outbox | Claims durable events with leases/fencing, retries consumers, and tracks pending/processing/published/dead state.   | It is transport infrastructure, not recipient inbox storage; it does not know notification channels or preference policy.                               |
| API record rules       | Combines company scope with registered row rules and applies the resulting domain to generic list/read/write flows. | A new recipient-owned model needs an explicit `recipient_id = authenticated user` rule; company scope alone is insufficient.                            |

## Decision and implementation contract

Add `@moonwitness/orm-notification` as an addon depending on `base` and `jobs`; do not overload `base.activity` or duplicate outbox delivery mechanics. Keep v1 delivery in-app only. Provide typed template and per-user/channel preference models, an inbox notification with delivery/read state and stable idempotency key, and a fake email adapter that records suppression in tests but has no network capability. Seed usable template and preference examples, but never seed a delivered message that looks like a real business event.

The addon consumer will validate outbox payloads from `unknown`, apply recipient/company preferences, create inbox rows with an event-derived idempotency key, and treat duplicate retries as success without inserting another row. API record rules must constrain regular users by both company and recipient; system/superadmin access follows the existing privileged policy. Board should show an inbox surface separately from activity reminders. Model access grants, navigation visibility, docs, tests, and generated references must ship with the addon.
